## CRITICAL — confirmed (4)

### ▶ [C1] TLS certificate validation is completely disabled for ALL API traffic in ALL builds, including the production App Store release
> **Partially addressed (2026-07-13):** bypass now gated to `!kReleaseMode` and restricted to the exact API host (`api_client.dart`). Release builds do full validation. **Blocked on server-side cert-chain fix (plan task 1.8)** before the bypass can be deleted entirely; until then the next release build will refuse to connect until the server cert is fixed.
- **Location:** `lib/core/network/api_client.dart:38`  ·  **Dimension:** security
- **Evidence:** // Accept server certificate (fixes CERTIFICATE_VERIFY_FAILED on iOS) (_dio.httpClientAdapter as IOHttpClientAdapter).createHttpClient = () {   final client = HttpClient();   client.badCertificateCallback = (cert, host, port) => true;   return client; };  This is unconditional — no kReleaseMode guard, no host restriction, no fingerprint check. It is the only certificate handling in the codebase (grep for badCertificate/SecurityContext/pinning confirms). It applies to every request the app makes: /auth/pin-login (username + PIN in body), /auth/refresh (refresh token in body), every Bearer-token header, all sales/customer/finance data to https://temurmchj.uz.
- **Impact:** Any attacker on the same network (shop Wi-Fi, hotspot, ISP-level) can present a self-signed certificate and the app will silently accept it — full man-in-the-middle. They capture staff PINs, JWT access/refresh tokens, and all business/customer/financial data, and can tamper with responses (prices, balances, shift totals) in a live money-handling POS. Because dart:io HttpClient does its own TLS (not governed by iOS ATS), the platform provides no backstop. The comment shows this was a workaround for a server cert-chain problem (likely a missing intermediate on temurmchj.uz); the correct fix is server-side. Note the workaround is also self-inconsistent: the fresh Dio() instances used for token refresh (auth_interceptor.dart:95) and retries (retry_interceptor.dart:26) do NOT have the bypass, so if the prod cert were genuinely invalid those paths would still fail — meaning the bypass is likely pure risk with no remaining benefit.

### ☐ [H1] RetryInterceptor blindly re-sends non-idempotent POSTs (quick-sale, cash operations) on timeout — duplicate financial transactions
- **Location:** `lib/core/network/interceptors/retry_interceptor.dart:26`  ·  **Dimension:** security
- **Evidence:** bool _shouldRetry(DioException err) {   return err.type == DioExceptionType.connectionTimeout ||       err.type == DioExceptionType.receiveTimeout ||       err.type == DioExceptionType.sendTimeout ||       err.type == DioExceptionType.connectionError ||       (err.response?.statusCode == 429); } ... final response = await Dio().fetch(err.requestOptions);  No method check and no idempotency key.
